# Spec: P4 — Narration script

**Status:** Approved
**Date:** 2026-09-12

Derived from `knowledge-explorer-spec.md` §12 phase P4 — *"Prompt, schema
validation, generation worker, per-block review screen, staleness detection."*
That document is the product source of truth and is locked except §14; this spec
adds only the implementation decisions P4 requires and the product spec does not
make. It assumes `specs/p1-curriculum/`, `specs/p2-authoring/` and
`specs/p3-images/` are delivered, which as of this writing they are.

## Problem statement

`narration_scripts` is an empty table with a `UNIQUE` constraint on `lesson_id`
and no code that reads or writes it. §11's `LlmProvider` has no interface. The
§6.5 staleness chain is built exactly one link deep: P2 computes
`lesson_contents.draft_content_checksum` and nothing consumes it.

P4 closes that gap and is the phase where the second of the product's two
AI-authored artifacts appears. It matters more than its own feature for three
reasons.

It is the first **text** generator, so it is where the §1.2 line gets enforced in
code rather than in prose: illustrations and narration are generated, lesson
bodies never are. FR-SCRIPT-02 states the constraint and names admin approval as
its enforcement point, which means P4 must build an approval that P5 can
actually refuse to synthesize without.

It is the first consumer of `draft_content_checksum`, so P4 decides what
staleness *means* operationally. §6.5 fixes the rule — computed on read, never
written by a job — but says nothing about granularity, and FR-AUDIO-01 requires
P5 to re-synthesize only the affected segments. Whatever P4 stores in
`script_segments` is the only evidence P5 will ever have about which block moved.

And it is downstream of P3 in a way that is easy to miss. FR-SCRIPT-03 writes a
figure's narration segment from the caption and the alt text — never from the
picture. P3 deliberately creates `lesson_images` rows with `caption_text = ''`
and leaves them empty until an admin types. An empty caption reaching this phase
is a paid call that produces a paragraph describing nothing, which P5 then voices.

## Acceptance criteria

### The provider interface

- `packages/ai` exports `LlmProvider`, its request and response types, and an
  injection token `LLM_PROVIDER` (a `Symbol`, following `EMAIL_PROVIDER` from P0
  and `IMAGE_GENERATION_PROVIDER` from P3). The token and the environment
  variable below deliberately share a spelling — unlike P3, whose interface name
  carried a word (`IMAGE_GENERATION_PROVIDER` / `IMAGE_PROVIDER`) that could be
  dropped. Prose distinguishes them as "the `LLM_PROVIDER` token" and
  "`LLM_PROVIDER=anthropic`".
- `complete(request)` takes a **fully composed** prompt and resolves to the
  model's raw text plus `modelName`, `providerName`, `inputTokenCount` and
  `outputTokenCount`. The provider never touches the database, the queue or
  object storage, and knows nothing about blocks, segments or checksums. It
  turns a prompt into text and reports what it cost.
- Token counts are on the response because §8 gives `narration_scripts` an
  `input_token_count` and an `output_token_count` column and nothing else can
  supply them. They are summed across a run's chunks.
- Two implementations ship. `AnthropicLlmProvider` calls the Messages API.
  The model identifier defaults to `claude-sonnet-5` per §6.3 and is
  overridable by `ANTHROPIC_MODEL`; the exact identifier and its pricing are
  verified against current documentation at implementation time and recorded in
  the adapter, the same discipline §6.3 demands and P3's OpenAI adapter follows.
- `FakeLlmProvider` is deterministic: the same prompt yields byte-identical
  output on every run. It parses the block manifest out of the composed prompt
  and emits one syntactically valid segment per block, so it exercises the real
  validation path rather than short-circuiting it. It also honors escape
  hatches the tests use to force each §6.3 rejection — a short count, an unknown
  `blockId`, a transposed order, unparseable output — so the retry ladder is
  testable without a network. `providerName` is `fake` and `modelName`
  identifies the fake's version, so a row generated by it is never mistaken for
  a real one.
- Selection is by environment, in `packages/ai/src/provider-factory.ts` beside
  `createImageGenerationProvider`: `LLM_PROVIDER=anthropic` uses the real
  adapter, anything else — including unset — uses the fake. `anthropic` with no
  `ANTHROPIC_API_KEY` throws at construction rather than downgrading silently,
  for the reason P3 records: a silent downgrade is a deployment quietly serving
  fake output that nobody notices until a learner does.

### The prompt (NFR-08)

- `packages/ai/src/narration-prompt.ts` holds one versioned template with an
  exported version identifier, and composes §6.3's input: the block manifest,
  `lessonTitle`, `learningObjective` and `languageCode`. Every §6.3 prompt
  constraint is expressed in the template; this spec does not restate them.
- **`lessons.learning_objective` is nullable.** When it is null the template
  omits the line entirely rather than sending an empty field or the word
  "null" — a labelled blank invites the model to fill it in, which is exactly
  the added knowledge FR-SCRIPT-02 forbids.
- **`courses.language_code` defaults to `vi`, not English.** The output language
  is the course's, per FR-SCRIPT-01, and the default install narrates in
  Vietnamese. Nothing in the template, the fake, or any assertion may presume
  English — see the verification section, where every content assertion is
  language-neutral.
- Unlike P3, the template version is stored in a **column** —
  `narration_scripts.generator_prompt_version` exists — so the composed prompt
  does not need to carry its own version marker and is not persisted at all.
  `generator_model_name` likewise records what answered.
- Changing the template requires incrementing its version identifier. Existing
  rows are never rewritten.
- The template is composed once per chunk at generation time in the worker, not
  at enqueue time. This differs from P3, which composes at enqueue so a retry
  cannot use a newer template than the admin saw. Here there is nothing the
  admin saw — narration takes no admin-authored prompt text — and the input is
  the block list, which the worker must read anyway.

### The generator's input projection

- `packages/ai` receives a `NarrationInputBlock[]`, not `Block[]`. The
  projection adds what §6.3 and FR-SCRIPT-03 need and drops what would only
  waste tokens:
  - every block contributes `blockId`, `blockType` and its plain `text`;
  - a `figure` block additionally carries `figureNumber` and the **selected**
    image's `captionText` and `alternativeText`, because FR-SCRIPT-03 writes the
    segment from those two fields and from nothing else;
  - a `table` block carries `tableNumber`, its caption, its headers, and at most
    the first 5 data rows — §6.3's "at most 5 representative rows" is enforced
    by not sending the rest, so a long table cannot be read in full even if the
    model ignores the instruction;
  - `markdown` is never sent. It is the raw source slice; the renderer needs it
    and a narrator does not.
- Building the projection is the only place `lesson_images` and the block list
  are joined for narration purposes. The join is by `blockId`, never by figure
  number — the number moves when a figure is inserted above it (FR-EDIT-02).

### Chunking

- A run splits the block list into **fixed-size chunks of
  `NARRATION_CHUNK_BLOCK_COUNT = 25` blocks**, declared in
  `packages/shared/src/queues.ts` beside `JOB_MAX_ATTEMPTS`. No overlap, no
  carried context, no heading-aware boundary. 25 sits in the middle of the
  reliability curve: comfortably within what a model counts and orders
  correctly, while a rejected chunk re-spends 25 blocks rather than half a
  lesson. A ~60-block lesson runs as 3 chunks with 2 boundaries.
  - *Rejected:* a token budget with the previous chunk's tail resent as
    read-only context. It costs input tokens on every chunk and makes the
    validation in the next bullet a subtraction rather than an identity.
  - **Known gap, accepted:** a chunk boundary can fall mid-argument, so the
    first segment of chunk *n+1* may reintroduce a term the last segment of
    chunk *n* just defined, or refer to something a listener has not heard yet.
    The review tab is where an admin catches it; the boundary is not marked in
    the UI. If this proves common in practice, carried context is the fix and it
    is additive — nothing stored depends on the boundary rule.
- Each chunk is validated **on its own** against the blocks it was sent: §6.3's
  three rejection conditions (segment count differs, unknown `blockId`, order
  differs) plus unparseable output. Because chunks do not overlap, the check is
  an identity against that chunk's manifest and needs no windowing logic.
- After every chunk validates, the concatenation is asserted against the full
  block list — same length, same `blockId`s, same order — before anything is
  written. A stitching bug therefore fails the run rather than producing a
  script that is subtly misaligned with the lesson.

### The retry ladder

Two counters, nested, because a malformed response and a dropped connection are
different failures and only one of them is time-dependent.

- **Inside a chunk:** a validation failure retries in process, up to
  `NARRATION_CHUNK_MAX_TRIES = 3` attempts total (1 try + 2 retries, per §6.3,
  which fixes this number and leaves the other two to this spec). The
  retry prompt restates the violated constraint and the expected `blockId` list.
  No backoff — waiting a second does not make a model return the right number of
  segments.
- **Across the run:** total provider calls are capped at
  `NARRATION_RUN_MAX_CALLS = 40`. Crossing it fails the run immediately, so a
  pathological lesson cannot fan a per-chunk budget out into dozens of paid
  calls. Worst case is `3 × chunkCount`, so the ceiling binds only above 13
  chunks — past roughly 325 blocks, where refusing is the honest answer. All
  three constants live in `packages/shared` next to `JOB_MAX_ATTEMPTS`, which is
  where NFR-03's numbers already are.
- **Outside the handler:** only a transport or provider error — a timeout, a
  5xx, a rate limit — escapes to BullMQ, which applies NFR-03's three attempts
  with exponential backoff through the existing queue defaults.
- Exhausting the chunk budget or the run ceiling sets `script_status = 'failed'`
  with a reason naming the chunk and the violated condition, and does **not**
  throw — a prompt that the model cannot satisfy will not be satisfied by a
  fourth identical run three seconds later.

### Generation (FR-SCRIPT-01)

- `GET /admin/lessons/:lessonId/narration-script` returns the review model: the
  computed status, both checksums, the review and generator metadata, the
  estimated runtime, `canEdit` / `readOnlyReason`, one row per block in
  block-list order carrying the block's `blockType`, plain text, figure or table
  number, its segment and that segment's freshness, and any orphaned segments
  after them. A lesson with no script row returns the rows with null segments
  and `status: null`, so the tab can render the lesson before anything is
  generated. §9.3 lists only the two writes; an editor cannot render a screen it
  cannot read, which is the justification P2 and P3 both used for adding their
  content and images `GET`s.
- `POST /admin/lessons/:lessonId/narration-script` returns `202 { jobId }`. It
  takes no body: §6.3's input is entirely derived from stored state.
- Before enqueueing, the endpoint refuses — synchronously, spending nothing —
  when any of the following holds, each with its own `errorCode`:
  - the lesson's stored block list is empty (`SCRIPT_LESSON_EMPTY`);
  - a generation is already in flight (`SCRIPT_GENERATION_IN_FLIGHT`, see below);
  - any `figure` block lacks a selected image, or its selected image has an
    empty or whitespace-only `caption_text` or `alternative_text`
    (`SCRIPT_FIGURES_INCOMPLETE`). The response lists the offending
    `{ blockId, figureNumber, missing[] }` so the tab can link straight to each
    figure's drawer. This reuses P3's per-figure completeness computation rather
    than restating it;
  - the block count alone would need more chunks than `NARRATION_RUN_MAX_CALLS`
    allows (`SCRIPT_TOO_MANY_CHUNKS`) — the ceiling is checked before the first
    call, not discovered at the last one.
- The endpoint writes one `generation_jobs` row with
  `job_type = 'generate_narration_script'` and `target_entity_id = lessonId`,
  sets the `narration_scripts` row to `script_status = 'generating'`, and
  enqueues onto a new `narration-script` queue — all in one transaction, so the
  in-flight lock and the job row cannot disagree.
- The BullMQ payload carries only `{ generationJobId, lessonId, createdByUserId }`.
  The worker re-reads `draft_block_list` and recomputes its checksum at the start
  of the run, and records that checksum as `source_content_checksum`.
  - *Rejected:* snapshotting the block list into the payload, as P3 snapshots
    its composed prompt. A block list is unbounded where a prompt string is
    small, and Redis is the wrong place for it.
  - *Rejected:* aborting the run if the content checksum moves mid-flight. That
    converts an admin saving a typo into a `failed` script, which P6's checklist
    then blocks on. Re-reading and recording what was actually read keeps the
    invariant that matters: `source_content_checksum` always describes the block
    list the segments were generated from. An edit during a run yields a script
    that is born stale, which is correct and which the tab shows.
- The worker **re-checks** the figure-completeness precondition after re-reading,
  before the first call. The enqueue-time check exists to answer synchronously
  and spend nothing; the worker-time check closes the race where a figure was
  emptied between enqueue and execution.
- The handler runs inside P1's `withJobLifecycle` wrapper, so the
  `generation_jobs` state machine, the attempt counter and the failure message
  behave exactly as import's and image's do. Queue concurrency is bounded and set
  low: every job is a paid provider call.

### Concurrency

- A `POST` while `script_status = 'generating'` returns `409` with
  `errorCode: SCRIPT_GENERATION_IN_FLIGHT` and the in-flight `jobId`, so the tab
  attaches to that job's SSE stream instead of starting a rival run.
  `lesson_id` is `UNIQUE` on `narration_scripts` — two runs would race for one
  row — and two runs would also each compute a preserve-edits pass against a
  script the other had already replaced.
- The `generating` status is the lock, and `withJobLifecycle` clears it on
  success and on terminal failure alike, so a crashed final attempt does not
  wedge the lesson. A run that dies without reaching either path leaves the lock
  set; recovering it is an operations concern and is named in Open questions.

### What a stored segment holds

`script_segments` is a JSONB envelope, not a bare array, because §6.3's response
carries `totalEstimatedSeconds` alongside the segments and §8 gives it no column:

```json
{
  "segments": [
    {
      "blockId": "fig1",
      "segmentOrder": 0,
      "narrationText": "Figure 1 shows …",
      "segmentChecksum": "a91f…",
      "sourceBlockChecksum": "77c2…",
      "isEdited": false
    }
  ],
  "totalEstimatedSeconds": 412
}
```

- `segmentOrder` is 0-based and redundant with array order. It is stored anyway
  because P5 writes it into `audio_segments.segment_order`, which is `UNIQUE`
  per audio row, and deriving it from array position at that point would make
  P5 depend on JSON array ordering being preserved through Prisma's `Json` type.
- `segmentChecksum` is SHA-256 over the whitespace-normalized `narrationText`.
  **This is the field P5 diffs.** FR-AUDIO-01 requires regeneration to
  re-synthesize only stale segments, and §8 gives `lesson_audios` only a
  whole-script `source_script_checksum` and `audio_segments` no checksum at all.
  Without a per-segment hash there is no evidence anywhere in the schema for
  which segment moved, and FR-AUDIO-01 is unimplementable. The JSONB is P4's to
  shape, so this costs no migration.
- `sourceBlockChecksum` is SHA-256 over the block's semantic projection — the
  same projection `blockListChecksum` already hashes, per block. It is what the
  preserve-edits pass and the per-block staleness report both read.
- `isEdited` records that a human has touched the text since it was generated.
  It drives the regeneration warning and a badge in the tab.
- `totalEstimatedSeconds` is the sum of the model's per-chunk estimates. It is
  shown to the admin as an approximate runtime and is **never** read by P5,
  which measures real durations with ffmpeg. It is an estimate stored as an
  estimate.
- `narration_scripts.script_checksum` is SHA-256 over the ordered list of
  `(blockId, segmentChecksum)` pairs. It is what `lesson_audios.source_script_checksum`
  will point at, and the precondition token for the edit endpoint below.

### Checksums in `packages/content`

- `packages/content/src/checksum.ts` gains an exported `blockChecksum(block)`
  that hashes `canonicalJson(semanticProjection(block))` for a single block.
- **`blockListChecksum` is not touched.** Redefining it over the new per-block
  hashes would be tidier and would change every stored
  `draft_content_checksum`, marking every existing lesson changed for a refactor
  nobody asked for. The two functions are independent by choice.
- Narration segment types, their zod schemas, `segmentChecksum`,
  `scriptChecksum` and the staleness comparison live in a new
  `packages/content/src/narration.ts`. They belong beside the block checksums
  because they must use the same `normalizeBlockText` normalization and the same
  `@noble/hashes` primitive, and because the admin tab renders them in the
  browser — so they are bound by the isomorphism constraint and
  `test/isomorphic.spec.ts` covers them automatically.
- `packages/ai` does **not** import `packages/content`. It validates only the
  model's raw response shape — well-formed JSON, expected `blockId`s, right
  count, right order. Checksums, the preserve-edits pass and the database write
  belong to the worker, which imports both.

### Regeneration preserves unchanged edits

When a run completes, segments are reconciled against the previous script rather
than replacing it wholesale:

- a block whose `blockChecksum` equals the previous segment's
  `sourceBlockChecksum` **keeps the previous segment verbatim**, including a
  hand-edited `narrationText` and its `isEdited` flag;
- a block whose checksum differs takes the newly generated segment, with
  `isEdited` reset to `false`;
- a block with no previous segment takes the newly generated one;
- a previous segment whose block no longer exists is dropped.

Chunks are still generated for every block, including preserved ones. Skipping
them would mean asking the model to narrate a lesson it can only see half of,
and §6.3's per-chunk validation is an identity against the chunk's manifest.
The saving is the admin's work, not the token spend.

### Failure is all-or-nothing

- Segments are held in memory for the whole run and written in **one
  transaction**, only after every chunk has validated and the stitched list has
  been asserted against the block list.
- A failed run sets `script_status = 'failed'` with a reason and leaves
  `script_segments`, `script_checksum`, `source_content_checksum`,
  `reviewed_by_user_id` and `reviewed_at` **unchanged**. An admin's reviewed
  script is never replaced by a half-written one. The spend on the chunks that
  did succeed is lost, which is the price.
- **Consequence, stated so it is not discovered later:** after a failed
  regeneration the row holds good segments and a `failed` status. The status
  describes the last *run*; the segments describe the last *successful* run.
  FR-PUB-01 blocks publishing on a `failed` script, so the only way out is a run
  that succeeds. That is intended — the admin asked for a regeneration because
  the old script no longer matches the lesson.

### Approval (FR-SCRIPT-04)

- `PUT /admin/lessons/:lessonId/narration-script` accepts
  `{ scriptChecksum, segments?: [{ blockId, narrationText }], approve?: boolean }`.
- `scriptChecksum` is the value the tab loaded, and a mismatch returns `409`
  `SCRIPT_CONFLICT` — the same optimistic-concurrency shape P2 gave the content
  editor, for the same reason: two admins on one lesson.
- Editing a segment recomputes its `segmentChecksum`, sets `isEdited = true`,
  and recomputes `script_checksum`. `sourceBlockChecksum` is **not** touched — the
  segment still derives from that block; a human simply rewrote the words.
- **A hand edit keeps approval.** FR-SCRIPT-04 defines approval as recording
  `reviewedByUserId` and `reviewedAt` and says only that an edit stales the
  audio; it does not say approval is lost. The person editing holds the same role
  as the person who approves, so the edit is itself an act of review.
  - *Rejected:* clearing approval on every edit, which would make fixing one
    word cost a second approval click.
  - **Known gap, accepted:** an admin can therefore add a sentence of new
    knowledge after approval and P5 will voice it. FR-SCRIPT-02 names approval as
    the enforcement point for "adds no facts", and this decision narrows that
    enforcement to the state at approval time. Recorded here so P6 and P5 do not
    assume a stronger guarantee than exists.
- **A generation run always clears approval**, nulling `reviewed_by_user_id` and
  `reviewed_at` — including when the preserve pass happened to keep every
  segment. A run writes machine text that no human has read, which is exactly
  what approval attests against. The rule has no exceptions so that an admin can
  predict it without knowing what the diff did.
- `approve: true` is refused with `422 SCRIPT_NOT_APPROVABLE` when the computed
  status is `stale`, `failed`, `generating` or `pending`. Approving a stale
  script records a review of text the lesson no longer says.
  - `pending` is in that list defensively and is unreachable in P4: §8 defaults
    the column to it, but no row is ever created outside an enqueue, which
    writes `generating`. Naming it costs nothing and stops the guard from
    silently admitting the state if a later phase does create rows earlier.
- A `PUT` against a lesson with no `narration_scripts` row is `404
  SCRIPT_NOT_FOUND`, not a row created on the fly. There is nothing to edit
  before a run has produced segments.
- A `blockId` in the body that is not in the stored script is refused with
  `422 SCRIPT_SEGMENT_UNKNOWN`, and the whole request writes nothing — the same
  all-or-nothing rule `OwnerFieldGuard` applies to a mixed body.

### Staleness (§6.5)

- **`script_status` is never stored as `stale`.** The stored value is one of
  `pending`, `generating`, `ready` or `failed`. `stale` is produced on read, per
  §6.5's "computed on read, never written by a background job". §8.1 lists
  `stale` as an allowed value of the column and this phase declines to use it,
  which is a deliberate reading of §6.5 over §8.1 and is why it is written down.
- The reported status is `stale` when the stored value is `ready` **and**
  `source_content_checksum` differs from the lesson's current
  `draft_content_checksum`; otherwise it is the stored value. `failed` therefore
  outranks `stale`, because a failed run is the more actionable fact and a
  failed row is not `ready`.
- `GET /admin/lessons/:lessonId/staleness` ships in P4 reporting the
  content→script link only. **The response has no `audio` key at all** until P5
  adds one. A key that is always `null` teaches every client to skip it, and
  leaves P5 unable to distinguish "no audio yet" from "not implemented".
- The response names three disjoint sets, computed by comparing each block's
  `blockChecksum` against its segment's `sourceBlockChecksum`:
  - `changedBlockIds` — block and segment both exist, checksums differ;
  - `missingBlockIds` — block exists, no segment (added since generation);
  - `orphanedSegmentBlockIds` — segment exists, block is gone (deleted since).
  These drive the tab's per-row badges, and P5 reads the same computation to
  scope its re-synthesis.
- A lesson with no `narration_scripts` row reports `"script": null`, not a
  synthesized `pending` — absence and a pending row are different facts.

### The queue

- `NARRATION_QUEUE_NAME = 'narration-script'`, `narrationJobNames`,
  `GenerateNarrationScriptJobData` and the chunk constants are declared in
  `packages/shared/src/queues.ts` alongside the import and image queues.
  `apps/api/src/jobs/narration.queue.ts` is a sibling of `image.queue.ts`.
- Job ids are qualified `script:<n>`, for the reason P3 qualified `image:<n>`:
  BullMQ ids are a per-queue counter, so an unqualified id is ambiguous across
  three queues. `job-status.service.ts` resolves the new prefix.
- **P4 does not extract a shared queue abstraction**, and touches no P1 or P3
  producer. The note in `queues.ts` predicting extraction at the third queue is
  **amended** to record that the third arrived at P4, the extraction was
  reconsidered and deferred to P5's audio queue, and why — so the file's own
  reasoning does not quietly go stale. Leaving a comment that forecasts a
  decision already made is how a codebase starts lying about itself.

### Job progress and authorization

- The stream reports chunk-level progress through the existing BullMQ progress
  mechanism and the SSE endpoints P1 built: `{ done, total }` as each chunk
  validates, then a terminal event carrying the segment count. A retry inside a
  chunk does not move the counter — only a validated chunk does, so the bar
  never goes backwards.
- `apps/api/src/jobs/job-permissions.ts` gains
  `generate_narration_script: 'generateAndEditNarrationScript'`, and
  `generate_narration_script` joins `lessonTargetedJobTypes` so R-02 applies to
  watching it. That map is partial and deny-by-default; omitting the row would
  make the tab's own stream return 403 rather than leaking anything.

### The narration tab

- The lesson editor grows tabs. Narration is a **full-width tab**, not a drawer:
  the list is read top to bottom across the whole lesson, and a 320px drawer
  cannot show a block's text and its segment side by side. The images drawer is
  unchanged — an image belongs to one figure and a drawer is right for it.
- Each row shows the block's plain text read-only on the left and its editable
  narration on the right, in block-list order, with the figure or table number
  where there is one, an edited badge, and a per-row freshness badge from the
  three sets above. Orphaned segments are listed after the blocks, clearly
  marked as belonging to deleted content.
- **Generate flushes a dirty buffer first.** If autosave is pending, the tab
  awaits the content `PUT` and enqueues only after it lands; if the save fails,
  no job is enqueued and the save error is surfaced. This is the pattern
  `lesson-editor.tsx` already uses for a figure clicked while dirty
  (`pendingFigureNumber`). Without it an admin pays for a script of a paragraph
  they rewrote a second earlier.
- Regeneration over hand-edited segments shows a confirmation naming how many
  segments were edited and that approval will be cleared. Edits on unchanged
  blocks survive, so the dialog says that too rather than implying total loss.
- The tab renders read-only with a reason when the server says so, reusing the
  `canEdit` / `readOnlyReason` fields `lesson-content.service.ts` already
  computes from the same facts R-01 and R-02 use. The writes refuse
  independently of anything rendered.

### Role enforcement

- All three endpoints declare `@RequirePermission('generateAndEditNarrationScript')`,
  which is already in `packages/shared/src/roles.ts` and needs no change. §3
  allows `admin_owner` and `admin`; `learner` is refused.
- Guards are split by method exactly as `images.controller.ts` and
  `lesson-content.controller.ts` do: the controller declares `SessionGuard` and
  `RolesGuard`, and each write adds `PublishedLockGuard` and `AssignmentGuard`
  itself — so an admin can still *read* the narration of a lesson they may not
  write, and the tab explains itself instead of showing an error.

## Non-goals

- **Any TTS, audio or timing work.** No `TextToSpeechProvider`, no
  `lesson_audios` or `audio_segments` writes, no ffmpeg, no
  `total_character_count`. P4 stops at approved text. (P5)
- **The publish checklist gate.** P4 computes and exposes staleness but blocks
  nothing on it. FR-PUB-01's "no narration script is stale or failed" is built in
  P6, reading P4's endpoint.
- **Any learner-facing exposure.** No script text on any public endpoint,
  nothing added to `published_course_structures`, no `apps/learner-web` change.
  §9.4's `GET /lessons/:lessonId` ships in P7.
- **Per-segment regeneration.** No "regenerate just this one segment" action. A
  run regenerates the whole lesson, preserving unchanged-block edits; one bad
  segment is fixed by typing. One job shape, one code path.
- **A shared queue abstraction.** See above — deferred to P5 with a note.
- **Multiple voices, languages or scripts per lesson.** `lesson_id` is `UNIQUE`
  on `narration_scripts` and stays that way; the script's language is the
  course's `languageCode`.
- **Editing the prompt template from the UI.** It is versioned source (NFR-08).
- **Cost dashboards.** Token counts are recorded per §8; presenting them is P10.

## Constraints

- **Node 22.** Under Node 20 vitest dies with a rolldown native binding error
  that looks nothing like a version problem.
- **`packages/content` is isomorphic.** `narration.ts` may not import a Node
  builtin or a non-allowlisted dependency; `test/isomorphic.spec.ts` walks the
  import graph and fails the build. Hashing uses `@noble/hashes`, as
  `checksum.ts` does, never `node:crypto` and never the async `crypto.subtle`.
- **`emitDecoratorMetadata` stays `false`.** Every new Nest injection is an
  explicit `@Inject(Token)`.
- **No Prisma `enum`s.** `script_status` is a `String` validated by the existing
  `scriptStatusSchema` in `packages/shared/src/enums.ts`.
- **No migration is needed and none should be written.** Every column P4 writes
  exists. `script_segments` shape is application-level, and the `NOT NULL`
  `script_checksum` and `source_content_checksum` are satisfied with `''` on a
  row created for an in-flight first run — the same empty-string-over-migration
  choice P3 made for `caption_text`. `''` only ever coexists with `pending`,
  `generating` or `failed`, never with `ready`.
- **Never regenerate `20260911180121_init/migration.sql`.**
- Request bodies are validated with zod `strictObject` in the controller; every
  error carries an `errorCode` from `packages/shared/src/errors.ts`.
- Tests live in a per-workspace `test/` directory. `*.e2e-spec.ts` for suites
  that boot an app — both globs are listed explicitly in the api vitest config,
  and a file that never runs looks exactly like a passing one.
- **NFR-03** supplies the BullMQ retry policy through the existing shared
  constants; the queue sets them as defaults so no endpoint can enqueue work
  that retries forever.
- Provider concurrency is bounded and low. Every job is a paid call.

## End-to-end verification

From a clean checkout, with Docker running:

```
nvm use
docker compose up -d --wait
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm verify
pnpm --filter @knowledge-explorer/admin-web test:e2e
```

**Expected:** exit code `0` from both commands, every suite green, and no
`ANTHROPIC_API_KEY` required — the fake provider is the default and the only one
CI exercises.

**1. Provider contract** (`packages/ai/test/llm-provider.spec.ts`) — no network,
no database:

- the fake returns one segment per manifest block, byte-identical across two
  calls with the same prompt;
- its forced-rejection hooks each produce exactly one §6.3 violation: short
  count, unknown `blockId`, transposed order, unparseable output;
- each response carries a non-empty `modelName`, `providerName` and non-negative
  token counts;
- the Anthropic adapter, given a recorded response body, extracts the text and
  maps model, provider and both token counts — the parsing is tested even though
  the call is not made;
- selection: `LLM_PROVIDER` unset yields the fake; `anthropic` with no key
  throws at construction rather than falling back.

**2. Prompt composition** (`packages/ai/test/narration-prompt.spec.ts`):

- the composed prompt contains the lesson title, the learning objective, the
  language code and every `blockId` of the chunk;
- a figure block's manifest entry carries its figure number, caption and alt
  text, and a table block's carries at most 5 data rows **even when the block
  has 40** — asserted by counting rows in the composed string;
- no block's raw `markdown` appears anywhere in the prompt;
- the exported version identifier is non-empty and is what gets written to
  `generator_prompt_version`.

**3. Checksums and reconciliation** (`packages/content/test/narration.spec.ts`):

- `blockChecksum` is stable across a whitespace-only change to a block's text
  and changes when a word changes — the same normalization `blockListChecksum`
  uses;
- **`blockListChecksum` output is unchanged by this phase**, asserted against
  hard-coded hex fixtures added in P2, so the refactor cannot silently restate
  every lesson's `draft_content_checksum`;
- `segmentChecksum` changes on a word change and not on re-wrapping;
- `scriptChecksum` changes when any segment changes and when two segments are
  transposed;
- the reconciliation: given a previous script and a new block list where b3
  changed, b7 is untouched and hand-edited, b9 is new and b4 is deleted — b7
  keeps its edited text and `isEdited: true`, b3 takes generated text with
  `isEdited: false`, b9 is generated, b4 is absent;
- the three staleness sets are disjoint and correctly populated for that case.

**4. Narration API** (`apps/api/test/narration.e2e-spec.ts`) — boots the API
against the migrated database:

- `POST` on a complete lesson returns `202`, writes one `generation_jobs` row
  with `job_type = 'generate_narration_script'` and `target_entity_id` equal to
  the lesson id, and leaves `script_status = 'generating'`;
- a second `POST` while generating returns `409` carrying the first `jobId`, and
  writes no second job row;
- `POST` on a lesson with a figure whose selected image has an empty caption
  returns `422 SCRIPT_FIGURES_INCOMPLETE` naming that figure's number, and
  enqueues nothing — asserted by the queue being empty;
- `POST` on a lesson whose figure has no selected candidate at all is refused
  the same way;
- `POST` on a lesson with an empty block list returns `422 SCRIPT_LESSON_EMPTY`;
- `PUT` with a stale `scriptChecksum` returns `409 SCRIPT_CONFLICT` and writes
  nothing;
- `PUT` editing one segment sets `isEdited`, changes `script_checksum`, leaves
  `sourceBlockChecksum` alone, and **leaves `reviewed_at` populated**;
- `PUT` with `approve: true` on a ready script records `reviewed_by_user_id` and
  `reviewed_at`; the same call on a stale script returns
  `422 SCRIPT_NOT_APPROVABLE`;
- `PUT` naming an unknown `blockId` alongside two valid ones returns `422` and
  neither valid segment is written;
- the staleness `GET` reports `ready` immediately after a run, `stale` after the
  lesson body is edited, and names exactly the edited block in
  `changedBlockIds`; it reports `"script": null` for a lesson never generated;
- **the response body contains no `audio` key**, asserted explicitly so P5's
  addition is a deliberate change;
- a `failed` script that is also out of date reports `failed`, not `stale`;
- RBAC, extending `rbac.e2e-spec.ts`: a `learner` is refused on all three
  endpoints; an `admin` on a lesson assigned to another admin is refused both
  writes with `FORBIDDEN_NOT_ASSIGNED` but **succeeds on the `GET`**; an `admin`
  writing in a published course is refused with `FORBIDDEN_COURSE_PUBLISHED`
  while `admin_owner` succeeds;
- job-watch: an `admin` may stream their own narration job, and a `learner` may
  not.

**5. Worker** (`apps/worker/test/narration.spec.ts`) — spawns the worker against
the real database and Redis with the fake provider:

- a 60-block lesson produces exactly 60 segments in block-list order from 3
  chunks of 25, 25 and 10, and the run makes 3 provider calls;
- a chunk forced to return a short count twice then succeed produces a complete
  script and 5 total calls — the §6.3 ladder, asserted by call count;
- a chunk that fails all three tries leaves `script_status = 'failed'` with a
  reason naming the chunk, **leaves a previously approved script's segments,
  checksums and `reviewed_at` byte-identical**, and does not throw to BullMQ —
  asserted by the `generation_jobs` attempt count staying at 1;
- a provider that throws a transport error does escape to BullMQ and the
  attempt count reaches 3, per NFR-03;
- a run whose chunk count would exceed `NARRATION_RUN_MAX_CALLS` is refused
  before the first call;
- a successful run clears `reviewed_by_user_id` and `reviewed_at` **even when
  every segment was preserved**;
- `input_token_count` and `output_token_count` are the sums across chunks, and
  `generator_model_name` and `generator_prompt_version` are populated;
- a figure emptied between enqueue and execution fails the job at the
  worker-side re-check without a provider call;
- progress: the job emits `{done, total}` once per validated chunk, and a chunk
  that retried twice still emits exactly one progress event.

**6. Browser** (`apps/admin-web/e2e/narration.spec.ts`) — Playwright, owning api
and admin-web through `webServer` and spawning the worker in `global-setup.ts`:

- an admin opens a lesson, switches to the Narration tab, clicks Generate, and
  the chunk progress advances to completion; segments appear beside their
  blocks in order;
- **Generate with a dirty buffer**: type into the editor, click Generate before
  autosave fires, and assert the content `PUT` completes before the
  narration `POST` is issued — the network-order assertion that documents why
  the flush exists;
- editing a segment and saving leaves the approved badge in place; clicking
  Generate afterwards shows the confirmation naming the edited-segment count,
  and after the run the badge is gone;
- editing the lesson body marks exactly the touched block's row stale in the
  tab and the header shows the script as stale;
- Approve is disabled with a reason while the script is stale;
- a lesson with an uncaptioned figure shows the refusal with a link to that
  figure's drawer, and Generate stays available after the caption is filled in.

**7. Live provider** (`packages/ai/test/anthropic-narration.live.spec.ts`) —
skips unless `ANTHROPIC_API_KEY` is set, mirroring
`openai-image.live.spec.ts`. Run by hand when the pinned model changes:

- a real call on a 6-block fixture returns a response that passes §6.3
  validation unmodified;
- the figure block's segment contains the figure's **numeral** within its first
  clause (FR-SCRIPT-03). The assertion looks for the digit, never for an English
  word — the fixture course runs at the `vi` default, so "Figure" never appears;
- the response contains no markdown syntax characters and no bullet glyphs;
- the same fixture run at a second `languageCode` produces different text,
  which is the only cheap check that the language instruction is honored at all.

## Open questions

None blocking. Two decisions above are deliberate accepted gaps rather than
unresolved items, restated here so a planner does not reopen them:

- **A `generating` lock orphaned by a worker that dies without reaching a
  terminal state** leaves that lesson unable to start a new run, and P4 ships no
  recovery. `withJobLifecycle` clears the lock on success and on terminal
  failure, so this needs a process killed mid-run to occur. A stale-lock sweep
  belongs with P10's job alerting; the interim answer is a manual `UPDATE`.
  Named because it is the one state an admin cannot leave from the UI.
- **Chunk-boundary discontinuity ships untested.** No assertion can usefully
  check that the first segment after a boundary does not redefine a term the
  last segment before it introduced. The review tab is the control. If it proves
  a recurring edit in practice, carried context is the fix and it is purely
  additive — nothing stored depends on the boundary rule.

§14's open decisions do not touch this phase: the payment gateway blocks P8, the
grace period and free-preview count are configuration, and the SSML-marks
question affects P5's synthesis strategy only. §6.4's note that a marks-based
provider would force whole-lesson resynthesis is worth knowing here, because the
per-segment checksum this phase stores is what makes the per-segment alternative
possible at all.
