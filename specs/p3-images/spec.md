# Spec: P3 — Images

**Status:** Approved
**Date:** 2026-09-12

Derived from `knowledge-explorer-spec.md` §12 phase P3 — *"`ImageGenerationProvider`,
candidate generation, selection, caption and alt text, manual upload."* That
document is the product source of truth and is locked except §14; this spec adds
only the implementation decisions P3 requires and the product spec does not
make. It assumes `specs/p1-curriculum/` and `specs/p2-authoring/` are delivered,
which as of this writing they are — all 23 P1 tasks and all 28 P2 tasks are
checked.

## Problem statement

P2 gives `::figure` a parser, a stable `blockId`, a `figureNumber` assigned in
exactly one place, and a renderer that draws a numbered empty slot. Nothing
fills the slot. `packages/ai/src/index.ts` is still 0 bytes, `lesson_images` is
written by nothing, and the project has no object storage of any kind and no
external AI provider wired in anywhere — P0's `EmailProvider` logs to stdout.

P3 is the phase where the product's one AI-authored visual artifact appears
(§1.2: illustrations are generated, lesson text never is). Because it is first,
it carries more than its own feature. It stands up the object storage that P5's
audio segments and P8's signed media URLs both inherit; it puts a second
producer on the BullMQ substrate P1 built and deliberately over-built for this
moment; and it is the first real implementation behind a §11 provider interface,
which is where the shape of `LlmProvider` and `TextToSpeechProvider` gets
settled by precedent.

It is also a gate on everything downstream. FR-IMG-03 makes `captionText` and
`alternativeText` mandatory before a lesson may leave `drafting`, and §5.5 feeds
both into P4's narration generator — FR-SCRIPT-03 writes a figure's narration
segment *from the caption and the alt text*, never from the picture. An empty
caption here is a narration segment in P4 that describes nothing and audio in P5
that reads that nothing aloud. The fields are not metadata; they are the only
channel through which an image reaches a listener.

## Acceptance criteria

### The provider interface

- `packages/ai` exports `ImageGenerationProvider`, its request and candidate
  types, and an injection token `IMAGE_GENERATION_PROVIDER` (a `Symbol`,
  following `EMAIL_PROVIDER` from P0).
- `generate(request)` takes a **fully composed** prompt string and a
  `candidateCount`, and resolves to 1–N candidates, each carrying its bytes,
  content type, `modelName` and `providerName`. The provider never touches the
  database, the queue or object storage; it turns a prompt into bytes and
  nothing else.
- Two implementations ship. `OpenAiImageProvider` calls OpenAI's image API with
  `n = candidateCount` and decodes the returned base64 payloads. The exact model
  identifier and its pricing are pinned against current OpenAI documentation at
  implementation time and recorded in the adapter — the same discipline §6.3
  applies to the narration model.
- `FakeImageProvider` returns deterministic PNGs derived from a hash of the
  prompt and the candidate index: the same prompt yields byte-identical
  candidates on every run, and the N candidates of one request are visually
  distinguishable from each other. `providerName` is `fake` and `modelName`
  identifies the fake's version, so a row generated by it is never mistaken for
  a real one.
- Selection is by environment: `IMAGE_PROVIDER=openai` uses the real adapter,
  anything else — including an unset variable and an unset `OPENAI_API_KEY` —
  uses the fake. Starting the worker with `IMAGE_PROVIDER=openai` and no key is
  a startup failure, not a silent downgrade.

### The prompt (NFR-08)

- `packages/ai` holds one versioned prompt template with an exported version
  identifier. The template composes the admin's prompt text with the lesson
  title and the course `languageCode`, and adds the house illustration
  direction plus an explicit instruction to render no text, labels or numerals
  inside the image — FR-IMG-02 exists precisely because models are unreliable at
  that, so the template does not ask for it.
- The string stored in `lesson_images.image_prompt_text` is the **composed**
  prompt, and it carries the template version identifier at its head.
  `lesson_images` has no `prompt_version` column and P3 adds none; a stored row
  identifies the template that produced it from its own content, which satisfies
  NFR-08 without a migration.
- Changing the template requires incrementing its version identifier. Existing
  rows are never rewritten.

### Candidate generation (FR-IMG-01)

- `POST /admin/lessons/:lessonId/images/generate` accepts
  `{ blockReferenceId, imagePromptText, candidateCount }` per §6.2, validates
  `candidateCount` as an integer in 2–4, and returns `202 { jobId }`. The
  default when the field is absent is 4.
- The request is rejected with `422` if `blockReferenceId` does not name a
  `figure` block in the lesson's **stored** `draft_block_list`. Generation is
  never attached to a block that does not exist server-side.
- The endpoint writes one `generation_jobs` row with
  `job_type = 'generate_image'` and `target_entity_id = lessonId`, then enqueues
  onto a new `image-generation` queue. `blockReferenceId`, the composed prompt
  and `candidateCount` travel in the BullMQ payload; `target_entity_id` is the
  lesson because the column is a UUID and a `blockId` is not one.
- The worker handler runs inside P1's `withJobLifecycle` wrapper, so the
  `generation_jobs` state machine, the attempt counter and the failure message
  behave exactly as import's do. NFR-03's three attempts, exponential backoff and
  the queue-level defaults come from the same `@knowledge-explorer/shared`
  constants P1 defined. Queue concurrency is bounded and set low, because each
  job is a paid provider call.
- On success the worker writes each candidate's bytes to object storage **first**
  and its row second, so a row never points at an object that is not there. All
  rows for one job are inserted together after every object has landed. A
  provider call that throws writes nothing at all.
- New rows have `is_selected = false`, `image_source = 'ai_generated'`,
  `caption_text = ''` and `alternative_text = ''`. The two NOT NULL columns are
  satisfied with empty strings rather than a migration; emptiness is what the
  completeness check reads.
- A second generation for the same block **appends**. Earlier candidates stay
  visible and selectable, newest first. Nothing is replaced and nothing is
  deleted.
- `figure_number` on `lesson_images` is left `NULL` and is never written.
  §6.1 states that figure numbering is assigned during block extraction "and
  nowhere else"; a copy in `lesson_images` would be a second source of truth
  that goes stale the instant a figure is inserted above it. The figure number
  shown anywhere in P3 comes from the block list.

### Manual upload (FR-IMG-02)

- `POST /admin/lessons/:lessonId/images/upload` takes a multipart body with the
  file and `blockReferenceId`, and returns `201` with the created row.
- Accepted types are PNG, JPEG, WebP and SVG; maximum 5 MB. The type is
  determined by sniffing the file's own bytes, never from the declared
  `Content-Type` or the filename. A file whose sniffed type is not on the list,
  or which exceeds the limit, is rejected with `422` and a machine-readable
  error code, and nothing is written.
- **SVG is sanitized before storage and the sanitized bytes are what get
  stored.** Scripts, event-handler attributes, `foreignObject`, external
  references and `javascript:` URLs are removed. The admin sees the sanitized
  result in the drawer, so a file altered by sanitization is visible as such
  before it is selected. There is no path by which the original bytes are
  served.
- Every stored object carries its sniffed content type as object metadata, and
  every image in the admin UI is rendered through `<img>` — never inline SVG,
  `<object>` or `<iframe>`.
- An uploaded row has `image_source = 'uploaded'`, null `image_prompt_text`,
  `image_model_name` and `image_provider_name`, and the same empty caption and
  alt text as a generated one. Uploads are synchronous: no job, no queue, no
  `202`.

### Selection, caption and alt text (FR-IMG-03)

- `PATCH /admin/images/:imageId` accepts any of `isSelected`, `captionText` and
  `alternativeText`.
- Setting `isSelected: true` clears the flag on every other row for the same
  `(lesson_id, block_reference_id)` in one transaction, so the §6.2 invariant —
  exactly one selected candidate per block — holds at every point a reader could
  observe.
- **Caption and alt text follow the figure, not the candidate.** When selection
  moves to a different candidate, the previously selected row's `caption_text`
  and `alternative_text` are copied onto the newly selected row as part of the
  same transaction. The admin writes both once and may compare candidates freely
  without retyping. Unselected rows keep whatever they were left with; only the
  selected row's values are ever read.
- Writing a caption or alt text on a row that is not selected is accepted and
  stored, so the drawer's fields work before a choice is made.
- P3 enforces no minimum length and no content rules on either field. FR-IMG-03
  requires them to describe what the image shows rather than name it; that is an
  editorial standard the drawer states in its helper text, and P6's publish
  checklist is where it becomes a gate.

### Object storage

- A new workspace `packages/storage` holds an `ObjectStorage` interface, a
  MinIO/S3 implementation over the AWS S3 SDK, and the key-naming scheme.
  `pnpm-workspace.yaml` already globs `packages/*`, so it needs no change. It is
  imported by `apps/api` and `apps/worker` only.
  - This is a sixth package where §11's repository layout lists five. §11
    names "private object storage with CDN" as infrastructure but assigns it to
    no package, and the two candidates both fail: `packages/ai` is defined as the
    three AI provider interfaces, and `packages/shared` reaches the browser
    transitively through `packages/content`, so the S3 SDK cannot live there.
    The deviation is deliberate and recorded here.
- Object keys are derived from the lesson id, the block reference id and the
  image id, with the extension for the sniffed content type. Keys are minted in
  exactly one function; no caller concatenates one by hand. `image_file_url`
  stores the **object key**, never a URL — a URL embeds an endpoint and a
  signature, both of which change between environments and every ten minutes.
- `docker-compose.yml` gains a MinIO service with a healthcheck and a bucket
  created on first start. The bucket is private; no anonymous read policy is
  ever set.
- The same service is added to `.github/workflows/ci.yml` alongside the existing
  PostgreSQL and Redis services.

### Serving images to the admin

- The API mints short-lived presigned URLs. Expiry is 10 minutes, inside NFR-02's
  15-minute ceiling.
- `GET /admin/lessons/:lessonId/images` returns every figure block in the
  lesson's stored block list with its `blockId`, `figureNumber`, its candidates
  newest first, which one is selected, the caption and alt text, and a
  per-figure completeness flag. Each candidate carries a freshly presigned URL.
  §9.3 lists only the three writes; an editor cannot render a drawer it cannot
  read, which is the same justification P2 used for adding its content `GET`.
- **Presigning uses the browser-reachable endpoint, not the internal one.** Under
  Compose the API and worker reach MinIO at its service name while the browser
  reaches it on localhost, and an S3 signature covers the host — a URL signed
  for the internal endpoint fails in the browser with an opaque signature error.
  The public endpoint is a separate environment variable from the one used for
  writes.
- P3 mints no learner-facing URLs. §9.4's entitlement-gated
  `GET /media/:mediaId/signed-url` is P8's.

### Job progress and authorization

- `JobStatusService` is generalized to resolve a job across every registered
  queue instead of consulting the import queue alone, and `JobSnapshot`'s shape
  is unchanged so `apps/admin-web`'s mirrored type still matches.
- The job stream's authorization stops being hardcoded to
  `importCurriculumOutline`. A job's required §3 action is derived from its
  `job_type` — `import_course_outline` maps to `importCurriculumOutline`,
  `generate_image` to `generateAndSelectImages` — and a lesson-targeted job also
  applies R-02, so an `admin` may watch a job on a lesson they may write and gets
  `403 FORBIDDEN_NOT_ASSIGNED` on one they may not. This is the widening
  `jobs.controller.ts` records as P3's.
- `GET /admin/courses/:courseId/stream` from §9.3 is implemented: it emits a
  `JobSnapshot` for every non-terminal `generation_jobs` row whose target
  resolves to this course, and completes when none remain. P1 deferred it on the
  grounds that it needs more than one producer; `generate_image` is the second.
- The course stream **emits only what the caller could watch job by job.** It
  declares the broader of the two mapped actions, `generateAndSelectImages`, and
  then filters each snapshot through the same `job_type`-to-action mapping and
  the same R-02 check the per-job stream applies. An `admin` watching a course
  therefore sees their own image jobs and not the owner's import job, rather
  than the controller-level permission deciding for every job at once.
- The drawer subscribes per job, not per course, and the course stream is
  verified independently. Both exist because a per-course view is what P6's
  publish flow will need.

### The renderer

- `LessonBody` in `packages/content/src/render.tsx` takes an optional map from
  `blockId` to `{ url, captionText, alternativeText }`. A figure block with an
  entry renders an `<img>` with its alt text and a `<figcaption>` reading
  "Figure N — caption", matching how tables already render their caption. A
  figure block with no entry renders P2's numbered placeholder unchanged.
- The prop is optional and defaults to empty, so every existing call site and
  every existing test keeps working untouched. `packages/content` gains no new
  runtime dependency and stays isomorphic — the map is data handed in, not
  fetched.

### The editor drawer

- In the P2 split view, a figure placeholder in the preview pane is clickable
  and opens a drawer over the preview showing, for that one figure: its
  candidates as a grid, a prompt box with a candidate-count selector and a
  generate button, an upload control, and the caption and alt-text fields.
- **The drawer keys off the server's `blockId`, never the preview's.** P2's
  preview parses the editor's text with no previous block list, so the ids it
  displays are display-only and need not match the stored ones. Clicking a
  figure resolves the authoritative id from the **saved** block list the content
  endpoint returned, by the figure's ordinal position among figure blocks.
- Consequently: while the buffer differs from what the server has accepted, a
  click first flushes the pending autosave and waits for the new block list
  before opening. While the markdown fails to parse, figure placeholders are not
  clickable. A figure that has never been saved has no server id and cannot be
  opened.
- Generation shows live progress from the job stream and does not block editing —
  the admin can keep typing in the left pane with the drawer open, per
  FR-IMG-01. A failed job surfaces its `errorMessage` with a retry.
- Selecting a candidate updates the preview immediately: the placeholder becomes
  the image, through the renderer's new map.
- On a lesson the caller may not write — a published course for a non-owner
  (R-01), or a lesson assigned to someone else (R-02) — the drawer opens
  read-only with every control disabled, consistent with P2's read-only editor
  banner.
- NFR-09 binds this to 1280 px and wider. No mobile or tablet layout.

### Completeness and counters

- A lesson is **image-complete** when every `figure` block in its stored block
  list has exactly one selected `lesson_images` row whose `caption_text` and
  `alternative_text` are both non-empty after trimming. A lesson with no figure
  blocks is image-complete.
- The flag is computed on read and stored nowhere, following §6.5's rule for
  staleness. It is returned by the images `GET` and shown in the editor as a
  per-figure marker and a lesson-level summary.
- **P3 changes no status column.** `lessons.content_status` stays where P2 left
  it; the `drafting → ready` transition and the publish checklist that consumes
  this flag are P6's.
- NFR-05's image count is **derived, not stored**: the number of
  `lesson_images` rows with `image_source = 'ai_generated'`, per lesson and
  rolled up per course. P3 ships that derivation as a service method with tests
  and no usage table, no counter column and no migration. Because generation
  writes a row per candidate, the data NFR-05 asks for is captured by the
  feature itself.
- **§9.2's `GET /courses/:courseId/usage` is deferred, deliberately.** §3's
  permission matrix contains no action for viewing cost or usage data, and
  `packages/shared/src/roles.ts` denies by default, so the endpoint cannot be
  declared without either inventing a matrix row — a change to a locked spec
  section — or borrowing an unrelated owner-only action, which would make the
  guard chain lie about what it is protecting. P10 owns the cost dashboard, has
  P4's tokens and P5's TTS characters to report alongside images, and is the
  right place to raise the gap with the spec owner. P3 leaves the derivation
  ready for it.

### Role enforcement

- Every endpoint above declares `generateAndSelectImages`, which §3 grants to
  `admin_owner` and `admin`. No endpoint invents a permission action and the §3
  matrix in `packages/shared/src/roles.ts` is unchanged.
- All three write endpoints carry `PublishedLockGuard` and `AssignmentGuard`, so
  R-01 and R-02 apply to generating, uploading, selecting and captioning exactly
  as they apply to saving content. The reads carry session and role only, so an
  admin can see a published lesson's images read-only — the same split P2's
  content controller documents.
- `PATCH /admin/images/:imageId` resolves its guard target through the image's
  lesson, since the route carries no lesson id.

## Non-goals

These are out of scope for P3 and must not appear in its implementation.

- **Narration and audio.** No `LlmProvider`, no `TextToSpeechProvider`, no
  ffmpeg. P3 writes the caption and alt text P4 will read and reads nothing from
  either phase.
- **The `ready` transition, the publish checklist, and any status-column write.**
  P3 computes image-completeness and displays it. P6 acts on it.
- **`GET /lessons/:lessonId/staleness`.** Still P4's, with the first artifact
  that can actually be stale. Images have no position in the §6.5 checksum chain.
- **The learner app.** The shared renderer gains the image path; no learner route
  consumes it, and `learner-web` is untouched. P7 owns that.
- **Learner-facing signed URLs and entitlement gating.** §9.4's
  `GET /media/:mediaId/signed-url` is P8's. P3's presigning is admin-only and
  behind the session guard.
- **CDN, production object storage, bucket lifecycle rules, replication,
  backups.** Still local Docker Compose and the CI runner, as P1 and P2 both held.
- **Deleting anything.** Not orphaned rows whose figure block was removed, not
  superseded candidates, not their objects. A lesson-body edit never destroys a
  generated image, and no endpoint deletes one. Storage accumulates; reclaiming
  it is P10's operations work.
- **Reattaching an orphan.** Rows pointing at a retired `blockId` are invisible
  everywhere in the UI. There is no "unused images" list and no way to move an
  image to a different figure block.
- **Image editing of any kind:** crop, resize, rotate, annotate, background
  removal, format conversion, thumbnails, responsive variants or `srcset`. The
  stored object is served byte-for-byte as stored.
- **AI-written captions or alt text.** §1.2 and §5.4 make both the admin's work;
  generating them would defeat the reason they exist.
- **LLM-assisted prompt suggestion from lesson context.** The admin writes the
  prompt. `packages/ai` gains no LLM client in P3.
- **Per-course or per-category illustration style presets.** One house template,
  one version, applied to every generation.
- **Content moderation or safety classification** beyond whatever the provider
  applies on its own.
- **Bulk generation** across a lesson, chapter or course. One figure block per
  request.
- **§9.2's `GET /courses/:courseId/usage` and the cost dashboard.** P3 ships the
  count derivation and stops there, for the §3 reason recorded above. P10 builds
  both.
- **Changing the `::figure` dialect.** No arguments, no attributes, no inline
  image syntax. P2's contract is fixed and the parser is not touched.
- **A second real provider.** The interface exists so P8-era substitution is
  cheap; proving it with a second vendor is not P3's job.
- **A linter.** Still an open tooling question the harness records, and not P3's
  to settle — the same call P1 and P2 made.
- **Mobile or tablet layouts.** NFR-09 binds the admin portal to 1280 px.

## Constraints

- **P1 and P2 must stay green.** Both are complete as of this writing. P3's
  drawer lives inside P2's editor, its ids come from P2's block list, and its job
  plumbing extends P1's; a regression in either invalidates P3's verification.
- **The §8 schema is locked and P3 adds no migration.** Every column P3 writes
  already exists. Where the schema is awkward — NOT NULL caption and alt text on
  a candidate that has neither, a `figure_number` that must not be trusted — the
  spec works within it and says why above.
- **`generation_jobs.job_status` is settled.** The harness flags it as
  uncatalogued by §8.1 and needing resolution before P3. P1 resolved it:
  `queued`, `running`, `succeeded`, `failed`, declared in
  `packages/shared/src/enums.ts`. P3 consumes that and changes nothing.
- **Every enum-like value comes from `packages/shared/src/enums.ts`.** No
  workspace redeclares a literal union. `image_source` and `job_type` are
  already there; P3 adds no member to either.
- **`packages/shared` and `packages/content` must stay browser-safe.** They are
  imported by `admin-web` and by P2's isomorphism test, which asserts the
  parser's transitive import graph contains no `node:` builtin. No S3 SDK, no
  provider SDK, no `Buffer`-only code may enter either.
- **NFR-03:** every provider call runs in a background job, bounded concurrency,
  exponential backoff, three attempts maximum, using P1's shared constants.
- **NFR-04:** no HTTP request waits on the provider. Generation returns `202` and
  reports over SSE. Upload is synchronous only because it calls nothing external.
- **NFR-08:** the prompt is versioned and the version is recoverable from every
  generated row.
- **Security.** `OPENAI_API_KEY` and the S3 credentials are read by `apps/api`
  and `apps/worker` only and never appear in a `NEXT_PUBLIC_*` variable or in
  any response body. Uploaded bytes are never trusted: type by sniffing, size
  enforced before buffering the whole file, SVG sanitized before storage.
- **Determinism in CI.** The default provider is the fake, so `pnpm test` needs
  no key, makes no network call outside Docker, and produces byte-stable
  artifacts.
- **Toolchain unchanged.** Node 22, pnpm 10.33.4, TypeScript 5.9.3 with `strict`,
  `noUncheckedIndexedAccess` and `noImplicitOverride`. Tests in a per-workspace
  `test/` directory, Vitest for units and Playwright for the browser, matching
  every existing workspace.
- **No component library.** Tailwind and hand-rolled controls, as P2 decided.

## End-to-end verification

From a clean checkout, with Docker running:

```
docker compose up -d --wait
pnpm install --frozen-lockfile
pnpm db:migrate
pnpm test
pnpm --filter @knowledge-explorer/admin-web exec playwright test
```

**Expected:** exit code `0` from both commands, every suite green, and no
`OPENAI_API_KEY` required — the fake provider is the default and the only one CI
exercises.

**1. Provider contract** (`packages/ai/test/image-provider.spec.ts`) — no
network, no database:

- the fake returns exactly `candidateCount` candidates for 2, 3 and 4;
- the same prompt and index produce byte-identical bytes across two calls, and
  two different indexes of one request produce different bytes;
- each candidate carries a non-empty `modelName`, `providerName` and a content
  type on the accepted list;
- the OpenAI adapter, given a recorded response body, decodes the expected
  number of images and maps model and provider names correctly — the parsing is
  tested even though the call is not made;
- provider selection: `IMAGE_PROVIDER` unset yields the fake; `openai` with no
  key throws at construction rather than falling back.

**2. Prompt composition** (`packages/ai/test/image-prompt.spec.ts`):

- the composed string contains the admin's text verbatim, the lesson title, the
  language code, and the no-text-in-image instruction;
- it begins with the version identifier, and a stored prompt can be mapped back
  to its template version from that string alone.

**3. Storage and keys** (`packages/storage/test/*.spec.ts`) — against the MinIO
service:

- a written object reads back byte-identical and with the content type it was
  written with;
- two images of the same figure get distinct keys, and keys for different
  lessons never collide;
- a presigned URL fetches the object; one signed against the internal endpoint
  and requested against the public host fails — the assertion that documents why
  the two endpoints are separate variables;
- SVG sanitization: a fixture carrying `<script>`, an `onload` attribute, a
  `javascript:` href and a `foreignObject` comes back with all four gone and its
  drawable content intact.

**4. Image API** (`apps/api/test/images.e2e-spec.ts`) — boots the API against the
migrated database and MinIO:

- `generate` on a valid figure block returns `202`, writes one
  `generation_jobs` row with `job_type = 'generate_image'` and
  `target_entity_id` equal to the lesson id;
- `generate` with a `blockReferenceId` that is not a figure block in the stored
  block list returns `422` and writes nothing;
- `candidateCount` of 1 and of 5 are both rejected; absent defaults to 4;
- `upload` of a 6 MB PNG returns `422`; a PDF renamed `.png` returns `422` —
  sniffing, not the extension; a valid WebP returns `201` with
  `image_source = 'uploaded'` and null model and provider;
- `upload` of an SVG carrying a script stores sanitized bytes: fetching the
  stored object back shows no `<script>`;
- selecting a second candidate leaves exactly one row with `is_selected = true`
  for that `(lesson, block)`, and copies `caption_text` and `alternative_text`
  onto it;
- selecting a candidate on a *different* figure block of the same lesson does not
  disturb the first block's selection;
- the images `GET` reports `isComplete: false` while the caption is empty, false
  while alt text is whitespace only, and true once both are non-empty on the
  selected row; a lesson with no figure blocks reports true;
- a figure block deleted from the markdown and saved: its rows survive in the
  database and disappear from the `GET` — the orphan rule, asserted on both
  sides;
- the NFR-05 derivation counts only `ai_generated` rows, ignores uploads, and
  rolls up from lesson to course across two chapters;
- RBAC, extending `rbac.e2e-spec.ts`: an `admin` generating on a lesson in a
  `published` course gets `403 FORBIDDEN_COURSE_PUBLISHED`; on a lesson assigned
  to another admin, `403 FORBIDDEN_NOT_ASSIGNED`; on an unassigned lesson,
  success; the same admin's `GET` succeeds in every case; a `learner` gets `403`
  on all of them.

**5. Worker** (`apps/worker/test/image-processor.spec.ts`):

- a successful job writes N objects and N rows, all unselected, all with empty
  caption and alt text, and all carrying the composed prompt, model and provider;
- a provider that throws writes no object and no row, and the

- after three failed attempts the row is `failed` and the queue stops retrying;

**6. Job streams** (`apps/api/test/job-stream.e2e-spec.ts`, extending P1's):

- an `admin` not assigned it gets `403 FORBIDDEN_NOT_ASSIGNED` — the widening,

- the course stream emits for both an import job and an image job on the same

**7. Renderer** (`packages/content/test/render.spec.tsx`, extending P2's):

- a figure block with no map entry renders P2's placeholder, unchanged from the
  existing assertion;
- a figure block with an entry renders an `<img>` carrying the alt text and a

- the map is keyed by `blockId`, so an entry for a different block is ignored;
- the isomorphism test still passes: no `node:` builtin entered the graph.

**8. Browser end-to-end** (`apps/admin-web/e2e/images.spec.ts`, Playwright,
extending P2's suite) — the journey that proves a figure goes from empty slot to
illustrated:

1. Sign in as the owner, open a lesson from the curriculum tree, and type a
   heading, a paragraph and a `::figure`.
2. Wait for the save indicator to report saved.
3. Click the **Figure 1** placeholder in the preview; assert the drawer opens
   for that figure.
4. Type a prompt, leave the count at 4, click generate; assert progress appears
   and that typing in the left pane still works while the job runs — FR-IMG-01's
   non-blocking requirement.
5. When the job completes, assert 4 candidates are shown.
6. Select the second candidate; assert the preview's placeholder is replaced by
   that image without a reload.
7. Assert the lesson is reported not image-complete, and that the reason shown
   is the missing caption and alt text.
8. Write a caption and alt text; assert the lesson becomes image-complete and the
   preview's `<figcaption>` reads "Figure 1 — <caption>".
9. Select the fourth candidate instead; assert the caption and alt text are
   still filled in — the copy-forward rule, seen from the browser.
10. Generate again with a different prompt; assert 8 candidates are now listed
    and the previously selected one is still present and still selected.
11. Upload a PNG through the drawer; assert it appears as a candidate and can be
    selected.
12. Insert a second `::figure` **above** the first in the editor, wait for save,
    and assert the new one renders as **Figure 1** with an empty placeholder
    while the illustrated one is now **Figure 2** and still shows its image —
    the assertion that proves the image is bound to the `blockId` and the number
    comes from the block list.
13. Delete the empty figure's line, save, and assert the illustrated figure is
    **Figure 1** again with its image and caption intact.
14. Sign in as an `admin` in a second context, open a lesson in a `published`
    course, open its drawer, and assert every control is disabled and no write
    request is issued.

Steps 9, 12 and 13 are the phase's load-bearing assertions: caption follows the
figure, the image follows the `blockId`, and the number follows the block list.

  supported type, each with the pinned model name.

Run it by hand before shipping and whenever the pinned model changes.

**10. CI** — `.github/workflows/ci.yml` gains only the MinIO service. The new

## Open questions

**One, and it does not block implementation:**

- **The house illustration style.** The prompt template needs a visual direction —
  the adjectives that make every illustration in a course look like it belongs
  to the same course. No one has chosen it, and this spec will not invent one.
  Implementation proceeds with a plainly stated neutral default recorded in the
  template, and the owner revises it by incrementing the template version; §5.4
  requires no particular style and nothing downstream depends on the choice.

Everything else was settled during the interview: OpenAI behind the interface
with a deterministic fake as the CI default, MinIO under Compose with the
S3 SDK, object keys in `image_file_url`, presigned URLs against a separate
public endpoint, the new `packages/storage` workspace and its recorded deviation
from §11's layout, sanitize-on-upload for SVG, versioned prompt template with
the composed string stored, append-on-regenerate, keep-and-hide for orphans,
caption and alt copying forward on selection, image counts derived from
`lesson_images` rows, the click-to-drawer editor interaction, the per-course
stream, the widened job-stream authorization, and the image-completeness flag
without a status-column write.

§14's four open product decisions are untouched and none blocks P3.
